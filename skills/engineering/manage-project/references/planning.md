# Plan demonstrable outcomes

## 1. Bound the objective

Inspect the existing Linear work, project agreements, relevant system pages, and domain terms in root CONTEXT.md. Read only the parts needed for the proposed outcome. Identify the audience, intended result, constraints, exclusions, available people and resources, and delivery expectations.

Reuse accepted decisions. Ask only about choices that materially affect direction or scope; record safe assumptions and decision owners.

**Done when:** the objective and planning boundary are clear without inventing commitments.

## 2. Separate decisions from delivery

Identify uncertainties that could change the approach: behavior, data, feasibility, integration, architecture, capacity, or dependencies. Compare credible alternatives only where evidence can change the decision.

Keep a decision question distinct from an implementation item. Record the question, owner, needed evidence, and which work depends on it. Use authorized deep research for disputed facts or a prototype for behavior that must be observed. Each investigation has a stopping condition and a return to this objective; an unrun experiment remains proposed.

Retain a decision's current answer and evidence once, linking dependents to it. Use a separate Linear issue only when the decision needs independent ownership or follow-up. Do not convert unanswered questions into promises to deliver.

**Done when:** the next outcome has a defensible approach or an explicit blocking decision and evidence request.

## 3. Shape the nearest useful outcome

Use Linear's hierarchy only where it clarifies responsibility:

| Object | Purpose in the plan |
| --- | --- |
| Initiative | A broader objective spanning multiple projects, when needed |
| Project | A bounded result, not automatically one per repository |
| Milestone | A meaningful demonstrable stage within that project |
| Issue | A coherent piece of work with a checkable completion boundary |

Detail the nearest useful milestone; keep distant work coarse. Give planned work an outcome, scope limits, acceptance evidence, responsibility, dependencies, and delivery conditions using existing fields and templates. Keep implementation, tests, documentation, and verification together unless independent ownership or acceptance warrants separation.

For a solo or small effort, a few linked issues may be enough. Cycles are optional scheduling choices, not mandatory stages or release boundaries. Propose only hierarchy that helps actual coordination.

Use the [agreements reference](project-agreements.md) only when requested conventions or missing project decisions affect this plan. Planning does not provision Linear, integrations, or subscriptions.

**Done when:** the objective connects to a demonstrable outcome and a next actionable item, with dependencies and unresolved choices visible.

## 4. Review and hand over

Explain the path, trade-offs, exclusions, and uncertainties. Separate recommendations from accepted decisions. Link supporting research or system explanations rather than copying them into every issue; publish only shareable evidence within the approved scope.

Apply approved Linear changes through the entry point's write checks. Update accepted scope when evidence changes rather than accumulating contradictory active plans. Use [tracking](tracking.md) when selecting or handing off the accepted next item.

**Done when:** the intended result, next milestone or item, decision gates, and next authorized action are identifiable. Planning complete does not mean implementation complete.
