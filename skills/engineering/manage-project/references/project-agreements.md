# Establish project agreements

Use AGENTS.md for project instructions. For an exact authorized correction, inspect and change the relevant text only; do not start a full setup or planning exercise.

## 1. Inspect the project

Verify the repository and change destination. Read existing agreements, architecture boundaries, generated files, registration points, checks, documentation, and ownership. Follow configuration rather than duplicate easily discoverable commands. Establish only non-obvious constraints that prevent harmful or misleading changes, with their verified reason.

**Done when:** current facts and gaps relevant to the requested agreements are known.

## 2. Resolve project-specific decisions

Reuse established values; ask only about unresolved material choices:

- target environments, boundaries, compatibility, and deliberate verification exclusions;
- accountable owners, reviewers, shared resources, intake channel, and acceptance and delivery conditions;
- verified Linear workspace/team and applicable project links, native state meanings, priorities, and permitted agent actions;
- GitHub repository and PR-linking convention, including how automated statuses relate to required acceptance;
- useful entry points into docs/systems and root CONTEXT.md.

Linear is the work tracker for solo and group projects; project agreements supply its actual context and lightweight organization, not a new tracker selection. Selecting the method does not authorize provisioning, subscriptions, credentials, integrations, or external writes. Keep unavailable identifiers or permissions explicitly unresolved.

**Done when:** needed agreements are already established, accepted, or named as pending decisions.

## 3. Write accepted agreements and vocabulary

User-supplied exact changes or an accepted proposal authorize their corresponding local edit. Present materially new conventions before writing them. Preserve unrelated content and secrets; include only project-specific values and verified constraints not already carried by the shared method. Tool schemas, model inventories, and session paths remain with the environment.

Use AGENTS.md for project constraints and conditional pointers. Every project has a root CONTEXT.md for domain terms; use [vocabulary](vocabulary.md) and its template when establishing or changing it. System pages live in docs/systems and use implement's documentation procedure. Keep detailed system rules in those pages, not in AGENTS.md or the glossary.

Read the relevant terms and system pages when a task changes or depends on their contracts; avoid an instruction to load the entire documentation corpus. If an ordinary narrow task discovers a missing required document, report the gap and continue independent work; establish it within an authorized documentation or project-agreement scope rather than expanding the task silently.

Report written paths and whether instruction loading was actually verified. Preparing agreements neither installs skills nor configures Linear.

**Done when:** accepted agreements and domain definitions have their owning documents, conditional entry points resolve, and unconfigured or unverified parts remain explicit.
