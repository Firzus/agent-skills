# Plan demonstrable outcomes

Plan the result people need, not a catalogue of tasks or technology choices. A plan authorizes neither implementation nor external publication.

For work limited to project agreements, inspect only the relevant project evidence and use step 3 with its reference. Stop when that reference's completion criterion is met, then report the instruction result and loading limits. Use the full sequence below for project or milestone planning.

## 1. Establish the objective

Inspect the existing project, plans, agreements, and current state. Identify the intended experience or outcome, audience, constraints, available people and resources, exclusions, and delivery expectations. Resolve visible facts before asking.

Ask only about decisions that materially affect scope or direction. Record assumptions and unresolved questions without substituting an agent preference for a user choice.

**Done when:** the objective, boundaries, decision owners, and planning scope are clear.

## 2. Resolve consequential uncertainty

Identify risks that could change the plan: feasibility, data, integration, architecture, tools, resources, or dependencies. Reuse established choices when adequate. Compare credible alternatives only where evidence could change the decision.

Use a bounded investigation for disputed facts or a representative prototype for observable behavior when authorized. Keep unrun experiments as proposals. Technical feasibility and user acceptance need different evidence.

**Done when:** the next milestone has a defensible approach, or its blocking evidence and decision are explicit.

## 3. Define project agreements when needed

Read [project agreements](references/project-agreements.md) when creating or revising AGENTS.md, or when missing conventions block the plan. Keep project facts and choices there, personal language in personal instructions, and shared method in the core and skills.

Defining a tracking tool does not authorize provisioning, subscriptions, credentials, integrations, or external writes.

**Done when:** needed agreements are confirmed or explicitly unresolved; a project can proceed without an unnecessary tracker or invented configuration.

## 4. Build the nearest useful milestone

Express each milestone as an integrated, demonstrable outcome with scope limits, acceptance evidence, dependencies, ownership, and risks. Detail the nearest milestone; keep distant work coarse. Use only hierarchy levels that serve real coordination.

Derive coherent work items, each with an outcome and checkable completion boundary. Keep implementation phases within the item unless independent responsibility or acceptance justifies separation. Avoid a task per file or a large speculative backlog.

Reuse the agreed plan location or current task record. Link supporting evidence and unresolved choices rather than copying research dossiers. Any external tracking updates follow the project's authorized route.

**Done when:** the objective connects to a demonstrable milestone and a concrete next item, with dependencies and decision gates visible.

## 5. Review and hand over

Explain the proposed path, material trade-offs, exclusions, and uncertainties. Separate user-approved decisions from recommendations. Include the next authorized action and where a pilot must return.

Update the plan when accepted scope or evidence changes; preserve the reason for the current direction without presenting obsolete plans as active commitments.

**Done when:** the user can identify the intended result, next milestone, next work item, and remaining decisions. Report planning complete without claiming the product is built or released.
