# Benchmark: four arms on Windows

This adapts [leanrea's benchmark](https://github.com/aicodeking/leanrea/tree/main/bench) (macOS, 2026-10-16) to Windows and adds a fourth arm.

## Setup

- Machine: Windows 11 Pro (one machine), Node.js 24, Git Bash, JDK 21, Ghidra 12.1.4 (`GHIDRA_INSTALL_DIR` set for every arm), `ilspycmd`. Missing from PATH: `strings`, `jq`, `otool`, `go`. `rg` exists only through Claude Code's Bash tool.
- Agent: Claude Code 2.1.303 headless (`claude -p --model sonnet`), `--max-budget-usd 4` per run.
- Isolation: `--strict-mcp-config`, `--setting-sources project,local` (no user skills or settings), `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (no user `CLAUDE.md`, no memory), and no inherited `CLAUDE_*` variables. A control run confirmed that only built-in skills were visible and that no language instruction leaked.
- Every run starts in a fresh copy of its targets. The four arms of one task and repetition run side by side, as in leanrea's `run_all.sh`.

Arms:

- **none**: no skill, no MCP.
- **leanrea**: `/leanrea` with leanrea's `SKILL.md` (commit `09ba4aa`), no MCP. It targets macOS tools, unchanged here on purpose.
- **rea**: `/reverse-engineer-anything` with rea-agents@6.5.0 as an MCP server (207 tools) and its skill.
- **re**: `/reverse-engineer` with this repository's skill and MCP server (8 tools, cold cache inside each run).

Targets (Windows builds installed on the machine):

- Notion 7.39.0: `app.asar` and `app.asar.unpacked/`, and the addon `win_utils.node` (PE32+ x64).
- GitHub CLI 2.95.0: `gh.exe` (Go 1.26.4).

Tasks (prompts and keys in `tasks.windows.json`):

- **electron**: trace Notion's microphone (meeting) detection to the native module, the driving class and its two modes, and both IPC channels.
- **native**: exported JS names of `win_utils.node`, how microphone users are found, how the single-instance lock works.
- **go**: toolchain version, main package path, two dependency versions of `gh.exe`.
- **deep**: from the binary, the single-instance pipe and mutex name format, the wire protocol, and the peer check.

### Answer keys

leanrea's keys target Notion 7.35.1 for macOS (`mac_utils.node`) and Homebrew `gh`. Every key was rebuilt by hand for the Windows builds, with the evidence recorded next to it in `tasks.windows.json`:

- electron: the Windows polling path calls `getProcessesAccessingMicrophoneDebouncedWithResult`, not `getRunningInputAudioProcesses` (which is only reached through a separate request), and main broadcasts both the legacy and the `-v2` change channel, so both are accepted. The two modes asked by the prompt are now graded.
- go: read independently by this tool's parser and by REA's `inspect_go_binary` on the same file (same SHA-256), consistent with `gh --version`.
- native and deep: from the Ghidra decompilation of `win_utils.node`, with function addresses and line numbers. The Windows lock uses a `Global\` mutex and a named pipe instead of a Unix socket, and it performs no peer authentication.

Grading is by case-insensitive regex on the final answer, as in leanrea. `regrade.ts` re-scores saved answers when a key changes.

The median wall time of `re` is the lowest on every task. Its token use is the lowest on every task except go, where the no-skill arm is level (53k vs 54k).

### Gaps and their causes

- **Fewer turns, fewer tokens.** `re` answers the electron task from one `electron_surface` call (class, addon names, IPC channels grouped by call site), the go task from one `buildinfo` call, and the native and deep tasks from `binary_inventory` plus `decompile` (Ghidra once, then cached per run). The shell arms extract the asar, grep minified bundles and disassemble by hand: more turns, and every turn re-reads a growing context. REA pays for a 207-tool catalog and longer tool outputs.
- **Speed on electron.** Without a skill the agent searches the minified bundles at length; REA spends time in its broad analysis tools before narrowing down.
- **Remaining misses (6 of 324 key checks), all on deep:**
  - `exe` (re rep 3, leanrea rep 3, none rep 2): the answer did not establish that the FNV-1a hash input is the executable path from `GetModuleFileNameW`; it left the input as "a string argument" or "unknown".
  - `peer` (none rep 2): no statement on peer authentication.
  - `json` (rea rep 2 and 3): the payload was described as a length-prefixed string without naming its JSON encoding.
- **Long outliers.** REA electron rep 1 (423 s) and none electron rep 1 (678 s) waited on background shell tasks; leanrea deep rep 1 took 360 s. They inflate the sums, not the medians.

### Corrections made during the benchmark

- Two full runs were aborted and archived (`results/aborted-*.jsonl`): Ghidra refused dotted project paths such as `.re-cache` (fixed in `decompile`), then a late reply from a background shell task replaced the graded answer (the harness now grades the text of every result event).
- Some keys were broken by escaping (the pipe key could never match `\\.\pipe`, the deep peer key held control characters). They were rewritten and every arm was regraded with `regrade.ts`; the earlier grading is kept in `results/results.graded-with-broken-keys.jsonl`. After review, the peer key's bare `none` alternative was anchored to authentication wording; every score stayed the same.
- Runs with several result events had their turns and tokens counted for the last segment only. `run.ts` now sums segments; the one affected row (none electron rep 1) was recomputed from its saved segments.

## Limits

- One model (Sonnet), one machine, n=3 per cell. Regex grading can miss correct wording or accept a lucky mention.
- The keys were written by the author of one of the arms, from evidence that this tool helped produce (Ghidra output for native and deep). The evidence is listed so it can be checked independently.
- Cost depends on prompt-cache warmth across runs; token totals are the steadier measure.
- leanrea is used unchanged: its commands assume macOS, which is part of what this benchmark measures.
- The arms of one task and repetition run side by side, as in leanrea's harness: they compete for CPU (Ghidra in particular), which adds noise to wall times.
- The machine was not idle (other development servers ran during the benchmark); wall times carry that noise.
- Not exercised by this benchmark: Linux and macOS (synthetic fixtures only in the unit tests), APK/DEX (`jadx` was missing at the time), and `managed` on a real .NET assembly. Both `managed` routes were later tested on real files (an APK through jadx, a .NET assembly through ilspycmd), outside the benchmark.
